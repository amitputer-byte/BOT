# גן הכפל — חבילת הנחיות לקלוד קוד
## מעבר לפרופילים (multi-user), refactor-first

---

## 1. מטרת החבילה

לקחת את אפליקציית `גן הכפל` הקיימת — קובץ HTML יחיד, offline, vanilla JS — ולעשות לה שני דברים בלבד:

1. להעמיד אותה כפרויקט תחזוקתי (Vite + git) שבונה חזרה לקובץ יחיד deployable.
2. לרפקטר את שכבת השמירה לשכבת אחסון **מודעת-פרופיל**, כך שיהיו תמרי + אפשרות לפתוח משתמש נוסף — **בלי לאבד את ההתקדמות הקיימת**.

> כל פיצ'ר/משחק חדש הוא מחוץ לסקופ של החבילה הזו. רואים אותו ב-Backlog בסוף, אחרי שהבסיס יציב ובדוק.

---

## 2. עקרונות מחייבים (constraints)

- **אפס אובדן נתונים.** זו חזות הכל. כל פעולה על נתונים קיימים מצריכה גיבוי גולמי תחילה.
- **offline-first** — אפס תלות רשת בזמן ריצה (אין CDN, אין fetch חיצוני).
- **עברית RTL מלאה** — שום רגרסיה בכיווניות.
- **פרטיות** — שום ענן, שום tracking, שום egress.
- **לא לרגרס** — כל 10 המשחקים והפיצ'רים הקיימים (חנות, חיות, קישוטים, מפת עולם, דשבורד הורים, PWA) חייבים להמשיך לעבוד.
- **שינויים קטנים** — commits קטנים וברורים, טסטים ירוקים לפני ואחרי כל שלב.

---

## 3. תהליך עבודה (איך לעבוד)

1. **קרא קודם, כתוב אחר כך.** קרא את הקובץ הקיים במלואו והבן את מבנה השמירה לפני שאתה כותב שורה אחת של לוגיקה.
2. **אל תנחש את שם מפתח ה-localStorage** ולא את צורת ה-blob — אמת אותם מהקוד עצמו.
3. **הצג מפה לפני רפקטור.** לפני שאתה משנה שמירה, הצג לי מפה קצרה של מבנה ה-state הנוכחי (אילו שדות, איך הם מקוננים, מה שם המפתח).
4. **טסטים לפני לוגיקה.** הרץ את חבילת הטסטים הקיימת (engine + jsdom) וּוודא שהיא ירוקה כבסיס לפני שאתה נוגע במשהו.
5. **שום פעולה הרסנית בלי גיבוי גולמי קודם.**
6. **commit אחרי כל שלב**, עם הודעה שמתארת בדיוק מה השתנה.

---

## 4. שלב 0 — הקמת הפרויקט

- `git init`, ו-commit ראשון של הקובץ הקיים **as-is** בשם `baseline`. זו נקודת החזרה.
- הקם Vite (vanilla). הכנס את ה-HTML/JS הקיים. ודא שהוא רץ ב-dev ושהוא בונה ל**קובץ HTML יחיד עצמאי** (למשל באמצעות `vite-plugin-singlefile`) — כי זה פורמט ההפצה שאנחנו רוצים לשמר.
- חבר את חבילת הטסטים הקיימת לפרויקט (`node:test` + jsdom, כפי שכבר השתמשנו). אם אין סקריפט מוגדר — הגדר `npm test`.

**Definition of done לשלב 0:** `npm run build` מפיק קובץ יחיד שעובד offline, זהה-התנהגותית למקור; `npm test` ירוק.

---

## 5. שלב 1 — שכבת אחסון מודעת-פרופיל (הליבה)

זה לב החבילה. מתחלק לחמישה חלקים.

### 5a. שכבת אחסון אחת (storage layer)
- צור **מודול storage יחיד** שכל קריאה/כתיבה של state עוברת דרכו. אסור שיישאר `localStorage.getItem/setItem` מפוזר בקוד — הכל דרך השכבה הזו. זה ה-chokepoint שיהפוך גם מעבר עתידי ל-IndexedDB וגם versioning לשינוי במקום אחד.
- השכבה אחראית על: registry הפרופילים, מצביע הפרופיל הפעיל, והשמירה per-profile.
- הוסף שדה `schemaVersion` לכל בלוק שמירה, ו-framework מיגרציות פשוט (מיפוי `version → migrationFn`) כך ששינויי סכמה עתידיים בטוחים ובדיקים.

### 5b. מודל הפרופילים
- `Profile = { id, name, avatar, createdAt }`.
- מפתחות namespaced: registry במפתח אחד, וכל פרופיל ב-key נפרד (למשל `gankefel:profile:<id>` — אמת את הקידומת מול המפתח הקיים).
- מצביע `activeProfileId` נפרד.

### 5c. מיגרציה מהשמירה הישנה — **הקריטי ביותר**
- **זהה** שמירת legacy (המפתח הישן / חוסר `schemaVersion`).
- **לפני כל דבר אחר**: כתוב גיבוי גולמי של ה-blob הישן למפתח backup נפרד. שום מחיקה/דריסה לפני שהגיבוי קיים.
- צור פרופיל **"תמרי"** עם `id` מיוצר, והעבר את כל ה-state הישן תחתיו: mastery state, מלאי (coins / gems / pets / decor / skins), הגדרות, streak — **הכל**.
- **אידמפוטנטי:** הרצה שנייה היא no-op (לא יוצרת כפילות, לא דורסת).
- הצב `activeProfileId` לתמרי ו-`schemaVersion` מעודכן.

### 5d. זרימת UX
- **כניסה:** אם מתגלה legacy → מיגרציה שקטה לתמרי וכניסה ישירה. אחרת: 0 פרופילים → onboarding שיוצר את הראשון; ≥1 פרופילים → מסך בחירת פרופיל.
- **"הוסף משתמש"** — עם נעילת-הורה קלה (שאלת כפל פשוטה או מספר) כדי שילד לא יפתח פרופילים סתם.
- **החלפת פרופיל** מתוך האפליקציה.
- **דשבורד הורים** scoped לפרופיל הפעיל, עם מתג להחלפת פרופיל.

### 5e. טסטים (חובה — לפני שהשלב נסגר)
- **טסט מיגרציה:** seed שמירת legacy ריאליסטית → הרץ מיגרציה → assert שפרופיל "תמרי" קיים עם **כל** השדות; mastery נשמר; מלאי נשמר; streak נשמר; הרצה שנייה = no-op; הגיבוי הגולמי קיים.
- **טסט בידוד פרופילים:** שני פרופילים — התקדמות/מלאי באחד לא דולפים לשני.
- **רגרסיה:** כל הטסטים הקיימים עדיין ירוקים; כל 10 המשחקים עדיין נטענים (jsdom flow); RTL לא נשבר.

---

## 6. Definition of Done לחבילה כולה

- תמרי נכנסת ורואה את **כל** ההתקדמות שלה כאילו כלום לא קרה.
- אפשר לפתוח משתמש שני עם state נקי ונפרד משלו.
- אפס דליפה בין פרופילים.
- גיבוי גולמי של השמירה הישנה קיים על המכשיר.
- `npm run build` → קובץ יחיד offline עובד; `npm test` ירוק; היסטוריית git נקייה ומשולבת בשלבים.

---

## 7. מחוץ לסקופ (במכוון — זה ה-Backlog)

אחרי שהבסיס הזה יציב ובדוק, אלה הצעדים הבאים לפי סדר ערך (מתוך 10 ההמלצות):

1. רמות קושי גלויות + מסלול התקדמות נראה לעין.
2. העמקת הקוריקולום — משפחות אסטרטגיה (×4, ×9, ×6) ו-transfer items (גורם חסר, חילוק הפוך).
3. מעבר ל-IndexedDB + גיבוי אוטומטי תקופתי (שינוי במקום אחד — שכבת האחסון שכבר נבנתה).
4. ארכיטקטורת משחקים מודולרית (registry) להוספת משחקים זולה.
5. איזון כלכלה — תגמול קשור ללמידה ולא לזמן משחק.
6. נגישות — הקראת שאלות (Web Speech), גודל טקסט, מצב ידידותי-לדיסלקציה.
7. דשבורד הורים מנבא ("4 עובדות בסיכון", תאריך שליטה משוער) + השוואת פרופילים.
8. מסלול חזרה עדין אחרי הפסקה (re-onboarding).
9. משחקים נוספים מעל המינימום הקיים.

> **הסדר אינו מקרי:** שכבת האחסון של שלב 1 היא התשתית שעליה כל אלה יושבים בלי כאב.
